# 판매처별 ADB 수집 실행안

업데이트: 사용자가 대상을 이마트/코스트코/트레이더스/롯데마트로 확정했다. 아래 최초 제안의 롯데온 대상은 롯데마트로 대체하며, 최신 기준은 [one-click-scenarios.md](one-click-scenarios.md)다. 기존 LOTTEON 수집기는 유지하고 LOTTE_MART와 혼용하지 않는다.

상태: 계획. 앱 설치 여부, 패키지명, 실제 메뉴, 가격 노출 여부는 아직 기기에서 확인하지 않았다. 아래 경로는 조사할 동선이며 현재 앱에 해당 메뉴가 있다고 단정하지 않는다. 기본 대상은 현재 카탈로그의 4개 source다.

## 우선순위와 판매처별 방법

| 순서 | 판매처 | 조사/수집 동선 | 반드시 분리할 조건 | 채택/보류 기준 |
| --- | --- | --- | --- | --- |
| 1 | 이마트 | 앱 식별 → 선택 매장 확인 → 상품 찾기/주류 목록 진입점 조사 → 위스키 목록 순회 → 상세 화면에서 가격/용량 확인 | 지점, 일반가/회원가/쿠폰가, 행사 기간, 품절 | 1개 매장 20개에서 상품·가격·용량·조건을 근거와 대조한 후 확대. 가격 없이 재고만 보이면 재고 관측만 보존 |
| 2 | 트레이더스 | 이마트 앱 내부 별도 탭인지 독립 앱인지 확인 → 트레이더스 매장 선택 → 동일 수집 흐름 | EMART_TRADERS source, 지점, 회원 등급별 가격, 대용량/묶음 구성 | 동일 앱이어도 이마트 수집 상태/매장/데이터를 별도로 관리. 회원 조건 불명 가격은 공개 최저가에서 제외 |
| 3 | 롯데온 | 앱 검색 → 상품 상세 → 실제 옵션 선택 상태와 판매자·배송/픽업 조건 기록 → 기존 웹 수집 결과 대조 | 판매자, 옵션, 회원·쿠폰·카드 조건, 배송비, 수령 방식 | 기존 Playwright로 얻는 것과 동일하면 웹 경로 유지. 앱에만 노출되는 가격/조건이 있을 때 ADB 보완 |
| 4 | 코스트코 | 앱의 주류 가격 노출 여부부터 조사 → 가능할 때 상품/행사 상세 순회 | 온라인/매장 구분, 지점, 회원 조건, 행사 기간, 세트 수량 | 앱에 개별 주류 가격이 없으면 해당 가격 수집 불가로 보고. 가격 추정이나 온라인→매장 가격 복사는 하지 않음. 행사 이미지뿐이면 OCR 후보와 근거를 검토 대기열에 저장 |

홈플러스/데일리샷/포켓CU/우리동네GS는 사용자 대상 확정 후 확장한다. 픽업형 앱을 추가하면 선택 점포·수령일·재고를 가격 조건에 포함한다. 실제 앱 조사 전 패키지명/선택자/지원 가능 여부는 확정하지 않는다.

## ADB와 추출 도구의 역할

- PC Node.js runner가 지정 serial의 ADB 연결/앱 실행/캡처/작업 복구를 담당한다.
- 파일럿은 UI hierarchy dump로 text/content-desc/resource-id/bounds 노출을 확인한다. 운영 단계에서 요소 선택과 조건부 대기가 필요하면 작은 UI Automator 테스트 runner를 사용한다.
- XML의 상품/가격 텍스트를 우선 추출한다. UI 트리에 없는 이미지 텍스트만 상품 영역 캡처 후 OCR한다. Canvas/WebView에서 못 읽거나 캡처가 제한되면 그 화면은 미지원/검토로 남긴다.
- UI Automator는 ADB 자체의 OCR 기능이 아니다. OCR 엔진은 별도 모듈로 붙이며 첫 20개 이미지로 정확도를 검증한 뒤 선택한다.
- 한글 검색 입력은 기기에서 입력 방식 지원을 검증한다. 기본 ADB input text가 한글을 처리한다고 가정하지 않는다. 카테고리 탐색을 우선하고 영문 브랜드/사용자 입력도 대안으로 둔다.
- 고정 좌표 연타 대신 현재 패키지/화면 제목/상품 식별자를 확인하고 다음 동작을 수행한다. 각 단계는 제한 시간과 재시도 최대 2회를 둔다.

Android 공식 근거: [ADB](https://developer.android.com/tools/adb), [UI Automator](https://developer.android.com/training/testing/other-components/ui-automator).

## 한 앱의 작업 순서

1. 기기 serial, 앱 패키지/버전, 화면 크기, 로그인/성인 확인 상태, 선택 매장을 기록한다. 인증은 사용자 조작 후 이어간다.
2. 목록에서 상품 ID 또는 화면 상품 식별 정보를 확보한다. 최근 화면/상품 fingerprint를 비교해 반복 스크롤을 종료한다.
3. 상세에서 상품명·용량·도수·구성·각 가격·조건·재고·관측 시각을 추출한다. 화면의 현재 선택 옵션도 기록한다.
4. 상품 영역 증거(XML/캡처)와 원문 JSON을 로컬에 먼저 저장한다. 계정 이름/주소 등이 포함된 영역은 수집 대상에서 제외한다.
5. 상세→목록으로 복귀하고 마지막 완료 상품/스크롤 위치를 checkpoint에 기록한다. 검증된 상품 ID가 없으면 임시 fingerprint로만 관리하고 상점 ID로 위장하지 않는다.
6. 로그인 만료, 매장 변경, 연결 끊김, 같은 화면 반복, 앱 버전 변경 시 해당 작업을 중단하고 사유를 남긴다. 구매/쿠폰 사용/장바구니 조작은 수집 과정에 넣지 않는다.

## 데이터 구조 제안 — 아직 마이그레이션하지 않음

수집 결과를 현재 liquor_price에 바로 넣지 않고 원본 관측과 공개 가격을 분리한다.

| 계층 | 주요 필드/처리 |
| --- | --- |
| raw observation | run_id, observed_at, source, app_package/version, channel, store_id/name, source_product_id, 원문 상품명·가격·용량·조건, option/seller, stock_status, evidence_path, extraction_method |
| parsed candidate | amount, currency, volume_ml, alcohol_percent, pack_count, price_type, membership_tier, coupon/card 조건, 행사 시작/종료, matching_status, review_reason |
| 상품 연결 | 검증된 판매처 상품 ID 매핑 우선. 브랜드·제품명·숙성·용량·도수·세트 구성 일치 검사. 영한 종류 매핑은 표시/정규화에 사용하며 제품 동일성의 증거로 쓰지 않음 |
| 가격 제안 | liquor_id + source + channel + store + seller/option + condition_key로 비교 대상을 구별. 동일 run/상품/조건 재시도에는 idempotency key로 중복 방지. 새 run은 새 관측으로 기록 |
| 공개 read model | 일반가와 조건부 가격, 앱/온라인/매장 가격을 구분하고 수집 시각·매장·조건 표시. URL 없으면 허위 구매 링크 생성하지 않음 |

현재 PreviewCandidateInput에는 지점/앱 채널/회원 조건이 없고 프론트 vendor 행은 source를 key로 쓴다. 따라서 새 조건을 보존하는 관측/offer 계약과 UI key/조회 집계를 먼저 설계해야 한다. 같은 source로 기존 웹 가격을 덮어쓰는 방식은 사용하지 않는다. 기존 preview와 safety-gates의 상품 매칭·검토 개념은 재사용하되 조건 손실 없는 어댑터와 마이그레이션을 만든 후 ingest-write에 연결한다.

검토 대상: 가격 0/통화 미확인, 용량 누락, 세트 여부 불명, OCR 불확실, 상충 가격, 상품 매칭 다중 후보, 지점/회원 조건 불명. 화면에 수집 시각이 없으면 과거 갱신 시각을 추정하지 않고 실제 관측 시각을 남긴다. 수집 실패는 품절과 구별하고 기존 정상 가격을 0원으로 변경하지 않는다.

## 개발 단계와 완료 기준

| 단계 | 결과물 | 다음 단계 조건 |
| --- | --- | --- |
| A. 앱별 조사 | 패키지/버전, 화면 흐름, 로그인·매장, XML 노출 여부, 샘플 캡처 | 각 앱을 텍스트 추출 가능/OCR 필요/가격 미노출로 분류 |
| B. 이마트 파일럿 | 1개 매장·20개 원본 JSON 및 검토표 | 20개 전수 대조. 가격·용량·조건 오인식은 보류 또는 수정. DB 쓰기 없음 |
| C. 배치 안정화 | 50개 배치, 중단/재개, 재시도, 중복 검출 | 동일 배치 재실행 중복 0건, 실패 후 가격 훼손 0건. 회원가/품절/세트/팝업 사례 확인 |
| D. 판매처 확대 | 트레이더스/롯데온/코스트코별 adapter와 실패 사례 | 판매처별 표본 검증 통과한 범위만 운영 가능 표시 |
| E. 가격 통합 | 관측/조건별 offer 모델, 검토 화면, 기존 카탈로그 연결 | 매장/회원가 혼합 없음, 상품·가격 근거 추적 가능, DB 변경 전 계약/마이그레이션 검토 |
| F. 자동 실행 | 작업 스케줄러, 최근 성공/실패/검토 현황 | 첫 3회 배치 결과로 처리량과 실행 주기 결정 |

운영 초안은 새 상품 발견(카테고리 순회)과 기존 상품 가격 갱신(검증된 상세 경로) 작업을 분리한다. 현재 112개는 검색 보완 목록으로 쓰되 앱 전체 상품 목록이라고 취급하지 않는다. 처음에는 수동 실행, 안정화 후 하루 1회부터 시작하는 안으로 둔다. 고정 시간은 앱별 실측 상품당 소요 시간 × 상품 수 + 로그인/재시도 여유로 산정한다.

한 휴대폰에서는 앱별 작업을 순서대로 수행한다. 여러 앱을 동시에 제어하려면 기기를 나누고 기기당 하나의 작업만 배정한다. PC의 이미 수집한 원본 파싱/검증은 화면 제어와 별도로 실행할 수 있다.

## 운영 화면 제안

어드민에 수집 현황, 실행 이력, 검토 대기, 상품 매칭 화면을 둔다. 검토 화면은 원본 캡처/읽은 값/기존 상품 후보를 나란히 표시하고 연결·보류·제외를 제공한다. 배치마다 발견/수집/검토/실패/미지원 수, 마지막 성공 상품, 소요 시간과 다음 재개 위치를 남긴다.

## 착수 시 필요한 정보

- 대상 앱 목록과 우선순위, 연결할 Android 기기.
- 첫 기준 매장/지역과 회원 가격 포함 여부.
- 앱 조사 후 확인할 상품 가격 노출·XML/OCR 가능 여부.

현재 기기를 조작하거나 크롤러/DB를 변경하지 않았다. 이 문서는 구현 순서와 검증 기준을 구체화한 계획이다.
